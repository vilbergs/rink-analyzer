# Rink Replay on the web

How the desktop app becomes a web app with the curriculum inside it, written 2026-11-01. The
[study-tool note](curriculum-design.md) assumed the vault holds the lessons and the Mac app shows the
plays. A web app removes that split: one place to read a lesson, watch its play, answer its decision
point and see your progress.

The user-facing side (path, lessons, step types, progress) is in
[web-app-experience.md](web-app-experience.md).

## What is reused and what is rebuilt

The rule: **everything that decides where something is lives in Rust and runs in the browser as
WebAssembly. Everything that lays out text and controls is Svelte.** The GPUI app and the web app are two
shells over the same `rink-core`, the way the app and the `rink` CLI already are.

| Part | Today | Web | Why |
| --- | --- | --- | --- |
| Model, file format, migration, `sample()`, facts, validation, templates | `rink-core` | wasm, unchanged | Pure Rust, no platform code |
| Rink drawing (boards, lines, players, puck, orders, suggestion zones, ghosts) | `paint.rs` draws through GPUI | `rink-core::scene` builds a display list; GPUI and Canvas2D each paint it | GPUI has no wasm target, but its drawing is only filled polygons, strokes and labels |
| Meters to pixels, zoom, pan, flip, hit test | `transform.rs` in the app | `rink-core::transform`, in wasm | Pure math; what you click must match what you see on both shells |
| Suggestion check and ghost positions | `rink-core::review` | wasm | Already in core; the file read and write stay desktop only |
| Editing a play (drag, orders, puck, events, captions, undo) | `state.rs` in the app, 1800 lines | Move the pure parts into `rink-core::edit`, call them from both shells | One definition of "move this player at this time"; see Phase 2 |
| Timeline, inspector, toolbar, picker, caption strip, shortcuts | GPUI views | Svelte components | Layout, text and controls, which the DOM does better than custom painting |
| Playback clock, keyboard, mouse and touch gestures | GPUI | Svelte, calling into wasm | Platform input belongs to the shell |
| Saving plays | Files in a library folder | Browser storage first, a server later | The browser has no library folder |
| Claude review loop (`rink` CLI, skills, `rink open`) | Desktop | Stays desktop for now | It needs the CLI and the file system |
| Curriculum and progress | Obsidian vault | In the web app | The point of the web app |

### The scene

`paint.rs` builds every shape as a polygon in rink meters and maps it through one transform. There are
three kinds of shape: a filled polygon, a stroked polyline (open or closed, with a width and an optional
dash) and one line of centered text. So the scene is a list:

```rust
pub enum Shape {
    Fill { pts: Vec<Vec2>, color: Color },
    Stroke { pts: Vec<Vec2>, closed: bool, width_px: f32, dash: Option<[f32; 2]>, color: Color },
    Text { at: Vec2, text: String, size_px: f32, color: Color },
}
pub struct Scene { pub shapes: Vec<Shape> }
pub fn build(frame: &Frame<'_>, t: &RinkTransform) -> Scene;
```

Coordinates are screen pixels, already transformed, so a painter is a loop with a three-way match.
The GPUI painter is that loop over `PathBuilder` and `shape_line`. The web painter is the same loop
over a Canvas2D context. A still for a lesson note (proposal 7 in the study-tool note) is the same loop
over an SVG writer or `tiny-skia`, which closes that proposal almost for free.

Alternatives, and why not:

| Alternative | Problem |
| --- | --- |
| Draw the rink again in Svelte, from the `Snapshot` | Two renderers drift. The puck on the stick side, the ghost arrow rule, the order path dots would all be copied by hand |
| Let Rust own a `<canvas>` through `web-sys` | Rust then owns the DOM, resizing, device pixel ratio and events, which are the shell's job |
| Scene in rink meters, painter applies the transform | Line widths and font sizes are in pixels, so each painter would need the scale anyway. Pixels keep the painters dumb |

### The wasm boundary

`crates/rink-wasm` exposes one `PlayHandle` (parse with migration, serialize, duration, snapshot,
captions, events, entities) plus `scene(...)` and `hit_test(...)`. The Svelte app never computes a
position. It asks for a scene per frame and paints it. A frame is about 200 shapes, so JSON across the
boundary is fine to start; a flat `Float32Array` is the optimization if it ever shows in a profile.

Compiling `rink-core` for `wasm32-unknown-unknown` needs two changes: the file functions in `io.rs`,
`session.rs` and `review.rs` go behind a default `std` feature, and `uuid` gets its `js` feature on
wasm.

## The web app

Svelte, as a Vite project in `web/`, static output, no backend for the first version.

```text
web/
  src/lib/wasm/        # generated by scripts/build-wasm.sh (wasm-bindgen --target web)
  src/lib/rink/        # RinkCanvas.svelte: paints a Scene, owns zoom/pan/pointer, asks wasm for hit tests
  src/lib/timeline/    # Timeline.svelte: ruler, event and caption marks, feedback bar, keyframe lanes
  src/lib/inspector/   # play, selection, events, captions, warnings
  src/lib/curriculum/  # lesson list, lesson page, progress
  src/routes/          # /, /lessons/<id>, /plays/<id>
```

Layout follows the desktop window: toolbar, rink with the caption strip under it, inspector on the
right, timeline below. On a phone the inspector becomes a sheet and the timeline shrinks to the
transport bar plus the event lane.

### Curriculum inside the app

The lessons, the step types, progress and the screens are specified in
[web-app-experience.md](web-app-experience.md). In short: a lesson is a Markdown file for the prose and
a `.steps.json` for the interaction under `curriculum/`, over a play and its "wrong" variant. Grading
lives in the `rink-lesson` crate and reaches the browser through `rink-wasm`'s `LessonHandle`. Progress
is append-only attempt rows in browser storage behind one `ProgressStore` interface.

### Where plays live

- Curriculum plays ship with the app as static files from `curriculum/plays/`. They change through git,
  like the lessons.
- The user's own retraced plays are saved in the browser (IndexedDB) and exportable as `.rink.json`, so
  the desktop app and the `rink` CLI can read them.
- Reviews are read-only on the web for now. A later backend runs `rink` and the review skill and returns
  the `.review.json`.

## The desktop app stays

The GPUI app remains the editor Claude Code drives (`rink open`, `rink current`, autosave, conflict
handling). Nothing in it changes for the user. It gains the shared scene and, in Phase 2, shared editing,
which is also what makes a future "answer a suggestion by dragging the ghost" work on both.

## Phases

1. **Scene and wasm** (branch `web/scene`): `rink-core::scene` and `::transform`, GPUI paints the scene,
   the `std` feature, `crates/rink-wasm`, `scripts/build-wasm.sh`, and a Node smoke test. Pixel-identical
   on the desktop.
2. **Shared editing**: move the pure operations out of `state.rs` into `rink-core::edit` as one `Edit`
   enum applied to a `Play` (move, turn, order, give puck, retime, add or change an event or caption,
   roster, text). Undo becomes a stack of plays in either shell. The GPUI `PlayState` keeps playhead,
   selection, autosave and the review poll.
3. **Web viewer**: `web/` with the rink, caption strip, transport bar and event lane, loading the example
   and curriculum plays. This is the first thing to put in front of a phone.
4. **Curriculum**: lessons, lesson page, progress, quiz mode.
5. **Web editor**: drag, orders, events and captions through `rink-core::edit`; browser storage; export.
6. **Backend**: accounts, plays on a server, reviews through the CLI and Claude.

## Build and verification with swamp

The repo is a swamp repository. `workflows/workflow-web-build.yaml` runs three jobs in order: `check`
(fmt, clippy, test, as CI does), `wasm` (`scripts/build-wasm.sh`) and `web` (`npm ci && npm run build`
in `web/`). Pass `--input web=false` to stop after the wasm job.

```sh
swamp workflow validate web-build
swamp workflow run web-build
swamp workflow history logs web-build
```

The steps are `command/shell` behaviors, which swamp's own rules allow only because no extension covers
cargo or Vite (`swamp extension search cargo` and `vite` return nothing relevant). When the pipeline
settles, the honest swamp shape is a small local extension, `rink/build`, with `check`, `wasm` and `web`
methods that return structured results (test counts, wasm size) instead of stdout. Deploying the static
site is where swamp earns its place: `@swamp/cloudflare/*` already exists for Pages, so the deploy job
is a behavior, not a script.

## Follow-ups the viewer surfaced

- Export the clamped `zoomed` and `panned` from `rink-wasm`. The JS zoom math re-does what `RinkTransform`
  already does, and cannot see its clamping, so a pan can drift past the boards.
- Emit TypeScript types for `Shape`, `Caption` and `Event` from the Rust (a `typescript_custom_section`
  or `tsify`), so `web/src/lib/rink/paint.ts` stops hand-copying them.
- Parse the review once (`set_review`) instead of per frame in `scene()`.

## Open decisions

- **Hosting**: Cloudflare Pages or GitHub Pages for the static app. Cloudflare has a swamp extension.
- **Who the user's team is**: labels assume home is the user's team ("their LW" for away). A lesson
  drafted from the opponent's view would need `is_me` to drive that, not the side.
- **Scene transport**: JSON now, typed array if a profile asks for it.
